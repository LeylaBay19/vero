# Проверка цепочки приёмки

Установи исходную задачу, утверждённые изменения границ и критерии. При отсутствии критериев сохрани неизвестное и предложи кандидаты для решения пользователя; не объявляй собственную трактовку согласованной приёмкой.

1. Для каждого критерия сохрани точную формулировку, источник, обязательность и версию. При неясной обязательности не исключай его автоматически.
2. Пройди от фактического результата назад: свидетельство проверки → версия результата/реализация → решение дизайна, если применимо → спецификация → исходное требование. Покажи разрывы, противоречия и ограничения.
3. Для критерия поведения требуй доказательства фактического результата; текст спецификации, проект решения, существование теста и команда exit 0 с неподходящим покрытием сами по себе недостаточны. Для документного критерия проверь фактический документ по источникам и заданным условиям.
4. Используй `met`, `not-met`, `not-verified`, `not-applicable` с конкретным основанием. Непроверенное из-за среды — not-verified. Не превращай проваленный или заблокированный важный критерий в not-applicable. Отсутствующий кодовый этап в чисто документной задаче допускается как неприменимый по границам задачи.
5. Сверь замечания Review и их закрытие, применимость старых результатов после изменений. При изменении версии пересмотри затронутую цепочку и зависимые выводы.

Выход `acceptance-traceability.md`: `ID критерия | точный смысл/источник | спецификация | дизайн/основание неприменимости | фактический результат и версия | тест/доказательство | review-замечания | итог | пробел/ограничение`.

Проверяй связь, а не только наличие файлов. Не меняй результат, критерий или свидетельство ради положительного итога.
