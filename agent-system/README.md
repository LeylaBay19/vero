# Переносимая агентная система для Codex

Редактируемый источник системы — эта папка. Версия 1.3.0 содержит 13 ролей, 48 навыков, четыре пакета задач и отдельные контексты проектов. Общий ранний product-documentation включён в библиотеку; оркестрация универсальна и называется workflow-orchestration.

## Устройство

```text
agent-system/
├── core/                        Общие правила и контракты
├── agents/                      Канонические роли TOML
├── skills/                      Процедуры и их ресурсы
├── packs/
│   ├── product-documentation/    Документный маршрут и комплект
│   ├── software-development/    Маршрут разработки
│   ├── product-documentation-synthesis/  Сведение сложного продукта
│   └── platform-consistency/     Паттерны, согласованность сот и изменения
├── projects/
│   ├── template/                Контекст нового проекта
│   └── skud/                    Контекст текущей работы
└── adapters/codex/               Установка, обновление и тесты
```

Агент определяет ответственность; скилл — процедуру; пакет — состав команды, порядок и обязательные результаты; проект — язык, аудиторию, источники и предметные ограничения. Базовые определения не зависят от СКУД и текущих путей пользователя.

В каноническом TOML четыре обязательных поля: name, description, skills и developer_instructions. Необязательная пара model и model_reasoning_effort задаёт модель и усилие по умолчанию; для пробной политики допустимы low, medium и high. Старые и дополнительные профили без этой пары сохраняют совместимость. Поле skills — метаданные библиотеки. Адаптер формирует нативные TOML с name, description, developer_instructions и при наличии переносит пару настроек модели.

## Модели и расход

Правила выбора под конкретное поручение, условия Astra, ограничение контекста и учёт пробного режима: [MODEL_POLICY.md](core/MODEL_POLICY.md). По умолчанию роли используют GPT-6.1 Sol · medium, UX Analyst — GPT-6.1 Terra · medium. Ограниченное извлечение, оформление и выполнение готовых проверок оркестратор явно назначает GPT-6 Luna по таблице политики. Нормативную применимость назначает Sol · high; Astra используется адресно с обоснованием.

Редактируй значения по умолчанию в agents/*.toml и правила в core/MODEL_POLICY.md, затем запускай адаптер. Карта agent_models в active.json отражает сгенерированные настройки. Динамический выбор выполняет оркестратор средствами текущего инструмента, а не адаптер. Факт генерации не доказывает загрузку профиля или фактический выбор модели приложением; текущий основной чат автоматически не переключается. Запрошенные и подтверждённые параметры различаются в coordination.md.

В текущем инструменте именованные роли закрепляют модель и усилие. Когда поручению нужно другое сочетание, оркестратор использует default-субагента с явными model/reasoning_effort, fork_turns="none" и полными инструкциями требуемой роли. Если параметры совпадают, использует именованную роль. Условия и ограничения описаны в политике.

## Перенос в другой проект

Нужен Python 3.11 или новее; внешних Python-пакетов и API-ключа адаптеру не требуется. Скопируй папку agent-system в корень нового проекта. Исходники продукта, материалы СКУД, старые результаты и agent-migration переносить не нужно.

Из корня нового проекта сначала посмотри план:

```powershell
python .\agent-system\adapters\codex\deploy.py --target . --pack product-documentation --project template
```

Примени тот же выбор:

```powershell
python .\agent-system\adapters\codex\deploy.py --target . --pack product-documentation --project template --apply
```

Подключится пять ролей документного пакета: orchestrator, analyst, specification, review, verification. Основной маршрут analyst → независимый review → verification; specification используется по поручению для утверждённого будущего поведения.

Для двух доступных пакетов с документацией по умолчанию:

```powershell
python .\agent-system\adapters\codex\deploy.py --target . --pack product-documentation --pack software-development --default-pack product-documentation --project template --apply
```

Это устанавливает все восемь профилей, но не запускает все этапы и не разрешает изменение кода. Для реализации нужны соответствующая задача и сообщённое пользователем согласование дизайна.

## Сведение макетов, совещаний, документации и закона

Для расширенного документного маршрута выбери product-documentation-synthesis. В нём исходный контур Исследователь → Автор → Рецензент явно сохранён; добавлены UX Analyst, Regulatory Analyst и Source Reconciler, общая методология, проверка ветвлений и Testing документации.

```powershell
python .\agent-system\adapters\codex\deploy.py --target . --pack product-documentation-synthesis --project template --apply
```

Для сохранения всех доступных ролей подключи три пакета:

```powershell
python .\agent-system\adapters\codex\deploy.py --target . --pack product-documentation --pack software-development --pack product-documentation-synthesis --default-pack product-documentation-synthesis --project template --apply
```

Методология и её формы: [product-documentation-methodology](skills/product-documentation-methodology/SKILL.md). Новый пакет: [synthesis](packs/product-documentation-synthesis/README.md). Полный состав всех ролей и навыков: [CATALOG.md](CATALOG.md).

В расширении 4 новые роли и 18 новых скиллов, все прежние 8 ролей/23 скилла сохраняются. Технические Design и Implementation остаются в библиотеке для своих задач; UX — отдельная роль. Наличие доступных ролей не означает одновременный запуск всех. Конкретные Figma-ссылки, записи и нормативные документы выбираются в задаче; установка пакета не означает их изучение.

## Что генерируется

- `.codex/agents` — выбранные профили Codex.
- `.agents/skills` — выбранные скиллы, ресурсы и транзитивные зависимости.
- `.agent-system/core`, `packs`, `project` — рабочие копии правил, маршрутов и выбранного контекста.
- `.agent-system/active.json` — активные пакеты, пакет по умолчанию, роли и привязки навыков.
- `.agent-system/manifest.json` — владение сгенерированными файлами и контрольные суммы.
- Управляемый блок в AGENTS.md — входная точка. Чужие инструкции за его пределами сохраняются.

Редактируй исходники в agent-system, затем запускай адаптер. Ручную правку управляемого файла адаптер не затрёт: он остановится и попросит перенести/согласовать изменения. Иные чужие профили и скиллы не удаляются. При смене набора пакетов убираются только неизменённые файлы прежней управляемой установки, с резервной копией. Обновляемые файлы также сохраняются в `.agent-system/backups`.

Если существующий чужой файл побайтно совпадает с нужным, он используется как external и не становится собственностью адаптера: отключение пакета его не удалит. Отличающуюся чужую конфигурацию нужно согласовать отдельно. Параметр --adopt предназначен для первой миграции по заранее проверенным хешам, а не для принудительной перезаписи любых файлов.

Адаптер проверяет план целиком до записи и каждый файл перед изменением. Это не общая транзакция файловой системы: при внешней ошибке записи установка может остаться частичной. После устранения причины повтори ту же команду; резервные копии и манифест сохраняются для разбора. Не заявляй успешную установку при ненулевом коде завершения.

## Как наращивать систему

**Новый скилл:** создай skills/имя/SKILL.md с name и description во frontmatter. Добавь только нужные ресурсы. Если нужны другие скиллы, укажи `{"requires": ["имя"]}` в skill.json. Затем добавь ID в skills агента либо в role_skills выбранного пакета. Не копируй один и тот же скилл для разных агентов.

**Новый агент:** создай agents/имя.toml с четырьмя полями по примеру существующего профиля. Укажи ответственность, границы и базовые skills. Добавь ID в agents нужного пакета; если он выполняет этап, обнови workflow, required_artifacts и WORKFLOW.md. Код адаптера менять не требуется.

**Новый пакет:** создай packs/имя/pack.json и WORKFLOW.md. Ссылайся на существующие роли и скиллы; не дублируй их определения. Схема pack.json видна в двух готовых пакетах: id, schema_version, version, coordinator, agents, workflow, role_skills, required_artifacts.

**Новый продукт:** скопируй projects/template в новый каталог, поменяй id в project.json и заполни CONTEXT.md. Подключи его параметром --project. Предметные факты, термины и источники храни здесь, а не в универсальной роли.

## Как пользоваться после установки

В чате проекта задай сценарий, источники, ожидаемый результат, критерии и каталог выходов. Например:

```text
Используй пакет product-documentation и отдельных субагентов.
Опиши сценарий [название] по [материалы].
Сохрани полный комплект пакета в [каталог].
Раздели текущее поведение, планы и утверждённые требования.
Выполни независимый review и verification документных критериев.
Вопросы и противоречия передай мне, код не меняй.
```

Процессы исполняются в чате Codex через доступные инструменты, а не отдельным фоновым сервисом. Если запуск пользовательского профиля по имени недоступен, инструкции передаются субагенту явно. Такая передача не доказывает автоматическую загрузку профилей приложением.

## Проверка адаптера

```powershell
python -m unittest discover -s .\agent-system\adapters\codex\tests -v
```

Тесты используют изолированные временные проекты и проверяют перенос, идемпотентность, зависимости, расширение без изменения адаптера, конфликты локальных правок и сохранение чужих файлов. Если среда запрещает создание тестовых конфигурационных каталогов, требуется соответствующее разрешение среды. Эти проверки не подтверждают качество описания реального продукта.

## Согласованность сот платформы

Версия библиотеки 1.3.0: 13 ролей, 48 навыков, четыре пакета. Новый [platform-consistency](packs/platform-consistency/README.md) добавляет Platform Consistency Steward и семь процедур для продуктовых паттернов, сравнения услуг, исключений, влияния, RACI и обновления документации. Все прежние роли и навыки сохранены. Базовые пакеты можно использовать независимо.

Для полного состава из корня проекта сначала посмотри план, затем добавь --apply:

```powershell
python .\agent-system\adapters\codex\deploy.py --target . --pack product-documentation --pack software-development --pack product-documentation-synthesis --pack platform-consistency --default-pack platform-consistency --project template
```

Пакет не включает фоновый мониторинг источников: он задаёт процедуры и контракт будущего подключения. Без настроенных доступов и исполнителя обновления выполняются по поручению в чате. Примеры запросов и ограничения находятся в README пакета. Для изменения кода нужен маршрут разработки; документная правка не закрывает дефект продукта.
