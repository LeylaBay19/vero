# Влияние изменения паттерна

## Входы
Текущая и предлагаемая версии паттерна, точный diff и основание предложения, реестр услуг и применимости, исключения, зависимости документации и проверок. Если одна версия неизвестна, покажи ограничение сравнения.

## Процедура
1. Сопоставь стабильные ID инвариантов, параметров и условий. Различай редакционную правку, изменение поведения, области применения, UX и требований к доказательствам. Не объявляй изменение редакционным, если оно меняет условия, модальность или ветви.
2. Проследи зависимости `паттерн@версия → применимость → услуга/контекст → процесс/правило/экран → спецификация/проверка/документ`. Для каждой связи покажи источник и версию, известное влияние или неопределённость. Неизученная услуга не считается незатронутой.
3. Оцени совместимость и переход: какие услуги уже соответствуют, где нужна проверка/изменение, какие исключения требуют пересмотра, возможное сосуществование версий и условия завершения перехода. Не назначай дату миграции и обязательность без основания.
4. Подготовь варианты решения с последствиями и известными владельцами. До подтверждения храни новую версию как проект, а текущую — по её установленному статусу; не изменяй общий паттерн вслед за одной услугой незаметно.
5. После сообщённого решения обнови только разрешённые реестры и связи, сохрани историю версий. Зависимые выводы и доказательства пометь требующими актуализации до проверки новой версии. Для кода, UX, документации и проверок передай отдельные конкретные задания по действующему маршруту.

## Результат
Diff паттерна, матрица влияния и неизвестного, проект перехода и задания с основаниями. План миграции не доказывает её выполнение, а изменение карточки не подтверждает изменение услуг.
