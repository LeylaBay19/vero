# Выбор моделей и расход

Версия политики: 1.0, пробный режим. Основание — согласованное пользователем распределение моделей от 2026-10-30. Политика применяется к порученным задачам всех пакетов и не запускает работу сама по себе.

## Выбор под поручение

Оркестратор выбирает модель и усилие перед каждым назначением по содержанию поручения. Значения в профиле — начальная настройка роли, а не запрет выбрать другую модель для конкретной работы. Не дели цельное небольшое поручение между моделями только ради использования каждой строки таблицы.

| Поручение | Модель | Усилие |
|---|---|---|
| Оркестрация: зависимости, назначения, контроль готовности | `gpt-6.1-sol` | `medium` |
| Analyst: извлечение явно указанных фактов с локаторами | `gpt-6-luna` | `low` |
| Analyst: восстановление процессов, условий, исключений и зависимостей | `gpt-6.1-sol` | `medium` |
| UX Analyst: изучение макетов, экранов, состояний и переходов | `gpt-6.1-terra` | `medium` |
| Regulatory Analyst: извлечение положений и реквизитов без вывода о применимости | `gpt-6-luna` | `medium` |
| Regulatory Analyst: применимость и связь обязательств с требованиями | `gpt-6.1-sol` | `high` |
| Source Reconciler: сопоставление утверждений и классификация расхождений | `gpt-6.1-sol` | `medium` |
| Documentation Author: связная сборка PRODUCT.md | `gpt-6.1-sol` | `medium` |
| Documentation Author: оформление реестров и локальная правка без изменения смысла | `gpt-6-luna` | `low` |
| Specification, Design, Implementation: спецификация, проектирование, содержательная реализация | `gpt-6.1-sol` | `medium` |
| Implementation: небольшое однозначное изменение с понятной проверкой | `gpt-6-luna` | `medium` |
| Testing: выполнение готовых проверок и сбор фактических результатов | `gpt-6-luna` | `low` |
| Testing: выбор проверок и исследование причин ошибок | `gpt-6.1-sol` | `medium` |
| Review: независимая оценка результата | `gpt-6.1-sol` | `medium`; сложные изменения — `high` |
| Verification: критерии, результат и доказательства | `gpt-6.1-sol` | `medium` |

Профили широких исследовательских ролей analyst и regulatory-analyst, а также testing имеют `Sol · medium` по умолчанию: ограниченное извлечение или выполнение готового плана оркестратор явно назначает Luna. Так неопределённое поручение не попадает автоматически на модель для узкой задачи. UX по умолчанию использует Terra; остальные роли — Sol. Нормативную применимость явно назначай `Sol · high`.

## Повышение модели и усилия

- `medium → high`: много связанных условий, сложные исключения, существенные противоречия или найденные смысловые пропуски. Повышение должно иметь названную причину.
- `Luna → Sol`: нужна интерпретация и исследование либо после одного адресного исправления остался конкретный дефект при достаточных входных данных. Если необходимость исследования ясна заранее, сразу назначай Sol.
- `Sol → Astra`: отдельный трудный вопрос при достаточных источниках и существенных последствиях ошибки. Примеры: различение противоречия и разных областей действия; взаимодействие большого числа правил; последствия изменения нескольких процессов; трудный дефект; проверка существенного замечания review. Не требуется предварительно тратить цикл Sol, если сложность и причина назначения уже обоснованы.
- Для Astra используй `gpt-6-astra · medium`; `high` — при особенно сложном разборе с зафиксированной причиной. Передай конкретный вопрос, исходные свидетельства и применимый предыдущий разбор. Заранее укажи способ проверки ответа: таблица комбинаций со ссылками, проверяемое объяснение дефекта или иной критерий.
- `xhigh`, `max`, `ultra`, а также `none` и `minimal` не назначаются автоматически в пробном режиме. Иные уровни возможны по отдельному явному поручению пользователя с проверкой поддержки средой.
- Недоступный источник, неоднозначное новое бизнес-правило и решение о приоритете источников передаются человеку или на целевой сбор данных. Сильная модель не восполняет отсутствующий факт и не принимает продуктовые решения за пользователя.
- После одного цикла исправления без новых данных не повторяй тот же запуск. Покажи остаточный дефект и назначь обоснованный следующий шаг. Astra не запускается вслед за любой неудачей или ошибкой инструмента.

## Передача и фактический запуск

Передай исполнителю цель, роль и необходимые инструкции, версии и локаторы источников, область записи, выходной контракт, критерии завершения и уже найденные дефекты. Сохраняй доступ к оригиналам. Полную историю чата передавай только при названной необходимости; краткий пакет не должен терять ограничения и решения пользователя.

Если используется `spawn_agent` с поддержкой этих параметров, явно указывай `model` и `reasoning_effort`. Для ограниченного пакета используй `fork_turns="none"`, передавая инструкции профиля и обязательные входы явно. Наследование полной истории может не позволять изменить модель; проверяй контракт текущего инструмента.

В текущем Codex именованные роли с настройками в TOML имеют закреплённые модель и усилие: инструмент сообщает, что менять их нельзя. Используй именованную роль, когда оба параметра совпадают с поручением. Если требуется Luna, Astra, другое усилие или роль по имени недоступна, выбери `agent_type="default"`, `fork_turns="none"`, явно укажи модель/усилие и передай полные инструкции нужного профиля вместе с обязательными входами. Например, извлечение фактов аналитиком: default + gpt-6-luna + low с инструкциями analyst; нормативная применимость: default + gpt-6.1-sol + high с инструкциями regulatory-analyst. Название типа default не отменяет ответственность назначенной роли, её ограничения и независимость review. Не пытайся перебить закреплённую модель именованной роли параметрами запуска. Если среда не даёт такого способа, сообщи ограничение.

Нативные файлы `.codex/agents/<role>.toml` содержат `model` и `model_reasoning_effort` по умолчанию. В `.agent-system/active.json` карта `agent_models` показывает сгенерированные значения; это не журнал фактических запусков. Изменение профиля не переключает уже работающий основной чат. Если координатором служит основной чат, его модель определяется настройками приложения.

Проверяй, позволяет ли инструмент выбрать требуемую модель и усилие. При недоступности назови ограничение; не заменяй модель молча и не выдавай настройку TOML за подтверждённый запуск. Обновлённое описание инструмента может подтвердить загрузку настроек роли, но не расход токенов и не факт завершённого исполнения. Продолжай независимую работу доступными средствами в согласованных границах, оставляя неподтверждённый запуск отмеченным.

## Экономия с сохранением качества

1. Запускай только необходимые роли и стадии. Параллельно выполняй независимые поручения с разными выходами; параллельность сама по себе не уменьшает токены.
2. Сохраняй первичные факты с ID, версиями и локаторами. Последующие роли используют этот реестр, открывая оригиналы для своей проверки, спорных мест и пробелов. Не подменяй источники пересказами.
3. Проверки ссылок, ID, структуры и других формальных условий по возможности выполняй скриптами. Содержательную оценку сохраняй за назначенным исполнителем.
4. Оркестратор проверяет результат и необходимые доказательства, избегая полного повторения исследования. Он не подменяет обязательное независимое review и verification.
5. Сохраняй независимое review отдельным исполнителем, который не писал оцениваемый результат. Совпадение или различие моделей не определяет независимость.
6. Подробности сохраняй в артефактах, в чат возвращай краткий итог с дефектами, ограничениями и ссылками. Краткость не должна скрывать невыполненные критерии.

## Учёт и пробная оценка

В существующем coordination.md веди строки назначений: поручение/исполнитель, запрошенные модель и усилие, подтверждённые параметры запуска или ограничение их наблюдения, причина отклонения от таблицы, входы/выходы и результат. При исправлении добавляй отдельную строку, не затирай предыдущую.

Фиксируй доступные показатели расхода и времени с источником измерения, пропуски, точность ссылок и число исправлений. Если инструмент не сообщает токены либо фактическую модель, пиши «недоступно»/«не подтверждено»; запрошенное значение не является замером. Учитывай работу координатора, исполнителей и повторных запусков, если такие данные доступны. Не выводи стоимость API или расход лимита подписки из числа сообщений.

На первых порученных заданиях сравни извлечение фактов, сведение источников и подготовку итогового раздела. Не запускай искусственные повторы реальных исследований без поручения. Оставляй наиболее экономную комбинацию, проходящую критерии качества с учётом исправлений; недостаток измерений отмечай явно. Настройка политики не подтверждает экономию или качество на реальных материалах.

## Platform Consistency Steward

Паттерны, сопоставимость сот, исключения и анализ влияния: `gpt-6.1-sol · medium` по умолчанию. Для множества взаимодействующих условий применяй существующие правила повышения усилия; отдельный трудный вопрос с достаточными источниками может быть передан Astra по этой политике. Новая роль не меняет настройки прежних профилей.
