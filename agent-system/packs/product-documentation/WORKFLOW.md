# Пакет описания продукта

Назначение: восстановить продукт по разрозненным источникам и подготовить понятную аудитории проекта документацию. Маршрут по умолчанию: analyst → отдельный review → verification документных критериев → человек. Координатор — orchestrator.

## Analyst
Применяй product-documentation, его шаблоны и нужные базовые процедуры. Результаты задаёт pack.json. В них должны быть реестр источников, карта продукта, сквозные сценарии, бизнес-правила, сущности, статусы, права, FR/NFR, вопросы, карта экспертов и проект RACI. Для маленькой/частичной задачи согласуй границы с формулировкой поручения и явно объясни исключённые результаты; не объявляй полный пакет готовым по частичному набору.

Если сведений нет, сохраняй пробел и вопрос, не выдумывая содержимое. По умолчанию исследуемый продукт доступен для чтения. Статус чернового документа не запрещает описывать свидетельства: раздельно фиксируй as-is, описанное в источнике будущее поведение, утверждённое to-be и предложения.

Готовь вопросы экспертам по влиянию на описание, учитывая уже известные ответы. Карта знаний не равна полномочиям: RACI остаётся проектом до решения человека. Критерии NFR не придумываются; «быстро» сохраняется как непроверяемое требование с вопросом.

Технические analysis-report/system-map/impact-map создавай как приложения, если они нужны задаче; их наличие не заменяет клиентский набор. Общая проверка рабочего состояния сохраняет чужие изменения и не требует наличия Git.

## Specification
Подключается для формализации утверждённого ожидаемого поведения, если это поручено. Получает конкретные разрешённые основания и анализ; неподтверждённые планы не становятся обязательными требованиями. Обязательные результаты этого дополнительного этапа: approved-behavior-sources.md, behavioral-specification.md, specification-validation.md. Если оснований нет, готовь каталог и вопросы, сохраняя доступный черновой разбор Analyst.

## Review и Verification
Review отдельным исполнителем проверяет источники, сохранение ограничений, различие фактов и планов, полноту набора и понятность. Проверка качества продуктовых тестов не обязательна для чисто документной задачи; неприменимость test-adequacy-review фиксируется по границам.

Verification сопоставляет каждый критерий с фактическими документами и источниками. Если критерии не заданы явно, выдели кандидаты из поручения и не выдавай их за подтверждённую человеком приёмку. Проверка документации не подтверждает работу реализации. Обязательные пробелы не маскируются общим положительным итогом.

Этот пакет не запускает разработку, миграции или активные проверки работающего продукта. Если требуется технический проект или код, координатор предлагает соответствующий установленный пакет и необходимые входы в рамках поручения.
