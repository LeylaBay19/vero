Документация: сценарии авторизации и привязки Mos ID

Версия: 1.0  |  Назначение: техническое задание для вёрстки и фронтенд-разработки  |  Связанные системы: локальная аутентификация (логин/пароль), Mos ID (СУДИР, OAuth 2.0)

1. Общие положения

1.1. Термины и определения

ТерминОпределение
Локальная учётная записьУчётная запись, созданная в вашей системе с логином и паролем.
Mos IDЕдиный городской идентификатор (СУДИР). Внешний провайдер аутентификации, работающий по протоколу OAuth 2.0.
mos_idУникальный идентификатор пользователя, возвращаемый Mos ID после успешной аутентификации. Используется для связи внешней учётной записи с внутренней.
user_idВнутренний уникальный идентификатор клиента в вашей системе. Остаётся неизменным независимо от способа входа.
auth_providerПризнак способа входа: local_only (только логин/пароль), mos_linked (Mos ID привязан к существующей локальной учётке), mos_auto (создана автоматически при входе через Mos ID).
Привязка (linking)Процесс сохранения mos_id в запись существующего авторизованного пользователя.

1.2. Требования к интеграции с Mos ID

Согласно требованиям СУДИР, информационная система должна поддерживать протокол OAuth 2.0. Для интеграции необходимо подать заявку в ДИТ Москвы и получить client_id и client_secret.

Параметры подключения (внешний контур СУДИР):

ПараметрЗначение
URL авторизацииhttps://login.mos.ru/sps/oauth/ae
URL получения токенаhttps://login.mos.ru/sps/oauth/ht
URL получения данных пользователяhttps://login.mos.ru/sps/oauth/me
Запрашиваемые разрешения (scope)openid, profile
Важно: URL для получения данных в некоторых источниках указан как https://login.mos.ru/sps/oauth/me, в других — https://login.mos.ru/sps/oauth/ht. Рекомендуется уточнить актуальный эндпоинт в документации, полученной при подключении.

1.3. Схема данных (минимальная)

users:
  - id (PK, внутренний user_id)
  - login (уникальный, nullable для mos_auto до генерации)
  - password_hash (nullable для mos_auto до генерации)
  - mos_id (уникальный, nullable)
  - auth_provider (enum: local_only | mos_linked | mos_auto)
  - profile_data (ФИО, телефон, email — заполняется из Mos ID и/или локально)

2. Сценарий 1: Вход через Mos ID с автоматическим созданием логина и пароля

2.1. Цель

Пользователь, не имеющий учётной записи в системе, входит через Mos ID. Система автоматически создаёт для него локальную учётную запись, генерирует логин и пароль и показывает их пользователю один раз.

Результат: браузер перенаправляется на страницу авторизации Mos ID (внешний домен, вёрстка не требуется).

ЭлементОписание

Логика бэкенда:

  1. Система получает code от Mos ID, обменивает на access_token, извлекает mos_id и данные профиля.
  2. Проверяет: существует ли запись с таким mos_id?
    • Нет → создаёт новую запись: auth_provider = mos_auto, mos_id = <полученный>, генерирует login и password, сохраняет хеш пароля, заполняет профиль.

Генерация логина и пароля:

  • Логин: уникальный, например mos_ + короткий хеш (8 символов).
  • Пароль: случайная строка 12–16 символов (буквы верхнего/нижнего регистра, цифры, спецсимволы).

3. Сценарий 2: Стандартная регистрация с последующей привязкой Mos ID

3.1. Цель

Пользователь регистрируется классически (логин + пароль), затем система предлагает привязать Mos ID для расширения функционала. Привязка выполняется только из авторизованной сессии.

Шаг 3. Процесс привязки Mos ID

ЭлементОписание
ЭкранLoadingPage
Текст«Перенаправляем на Mos ID…»

Логика бэкенда:

  1. Пользователь уже авторизован (сессия активна). Это обязательное условие.
  2. Запускается OAuth-редирект с параметром state, привязанным к текущей сессии.
  3. После возврата из Mos ID система получает mos_id.
  4. Проверка: не привязан ли этот mos_id к другой записи?
    • Привязан к другой → экран ошибки (шаг 4).
    • Свободен → сохраняет mos_id в текущую запись, меняет auth_provider = mos_linked.

6. Логика бэкенда (сводка)

6.1. Обработка callback от Mos ID

1. Получить code из query-параметра
2. Обменять code на access_token (POST на URL токена)
3. Запросить данные пользователя (GET на URL данных, с access_token)
4. Извлечь mos_id
5. Ветвление:
   - Если сессия активна (пользователь уже авторизован):
       → это привязка. Проверить, не занят ли mos_id другой записью.
         - Свободен → сохранить mos_id в текущую запись, auth_provider = mos_linked
         - Занят → ошибка LinkConflictPage
   - Если сессии нет:
       → это вход. Найти запись по mos_id.
         - Найдена → авторизовать
         - Не найдена → создать запись (mos_auto), сгенерировать login/password,
           показать MosAutoAccountCreatedPage

6.2. Обработка входа по логину и паролю

1. Найти запись по login
2. Проверить password_hash
3. Авторизовать (создать сессию / выдать JWT)
4. Не зависит от auth_provider — все записи с валидным паролем могут входить

7. Примечания по интеграции с Mos ID

  1. Подтверждённая учётная запись. Для ряда сервисов может потребоваться полная (подтверждённая) учётная запись Mos ID. Это стоит проверить в требованиях к вашему конкретному функционалу.
  2. Уникальность mos_id. На уровне базы данных необходимо установить уникальный индекс на поле mos_id, чтобы исключить привязку одного Mos ID к двум разным записям.
  3. Процесс подключения. Интеграция с СУДИР — это организационно-технический процесс, включающий подачу заявки, тестирование и проверку со стороны ДИТ Москвы. Рекомендуется заложить время на бюрократические этапы.
  4. Один пользователь — одна учётная запись. Согласно спецификации Mos ID, один пользователь может иметь только одну подлинную учётную запись. Это соответствует требованию уникальности mos_id.
