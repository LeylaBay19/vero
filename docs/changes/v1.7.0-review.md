## Проверенные требования

- Контакты отделены от юридических данных: «Изменить контакты» открывает только телефон/email/сайт и требует director при открытии/submit. Реестровые сведения и руководитель readonly; отдельное обращение в поддержку сохраняет описание и цель, не изменяет компанию/полномочия.
- Выход получил видимый текст «Выйти» и использует прежний сброс сеанса.
- «Сервисы» — пробное название каталога. Вариант 1 показывает сервисы выбранной организации; вариант 2 — допустимые компании внутри карточки. На каталоге второго варианта скрыт глобальный selector, внутри услуги явны компания/роль.
- multi точно отражает описанные fixtures: ООО «Пример» — director организации, АГР/руководитель сервиса, НСМ/наблюдатель, ОССиГ/null; ООО «Вектор» — employee, АГР/наблюдатель, ОССиГ/специалист. Меню зависит от organizational kind, а не надписи роли другой соты. serviceRole при отсутствии назначения в multi не наследует соседний сервис.
- card-context при открытии услуги ищет выбранную компанию среди выданных contexts и проверяет её роль именно в целевом сервисе. Смена компании обновляет организационный контекст и меню. Недоступный сервис в варианте 1 предлагает сведения о подключении, не рабочую операцию.
- Последнее уточнение serviceSelections хранит выбор отдельно по сервису, допускает только имеющуюся неперсональную компанию с назначением и восстанавливает выбранное при возврате. Сброс/выход очищают выбор.
- Новая УКЭП не выдаёт director: verify формирует certificateData и ведёт review-company. Сведения владельца/компании видны перед подачей; checkbox обязателен. Только application-submit создаёт submitted-заявку; при несовпадающем ИНН сертификата submit не работает.
- Результат платформы применяется только отдельной демопанелью, для текущей submitted-заявки на её экране. До этого контекст руководителя не добавляется. approved создаёт context по ИНН с защитой от дубля; rejected не добавляет контекст. Повтор после отказа очищает certificateData и снова проходит УКЭП/просмотр/подтверждение/отправку.
- applications хранится по ИНН, повторный поиск submitted/rejected возвращает её статус. current application указывает на выбранную запись. Это состояние поданной заявки, а не возвращение удалённого черновика prepare/resume.

## Независимое исполнение логики

В Node VM исполнены реальные обработчики исходного HTML с заменой DOM, без подмены проверяемых функций. Passed:

1. verify приводит к review-company и оставляет только personal; преждевременный apply-platform-result ничего не выдаёт.
2. Без checkbox application не создаётся; после подтверждения submitted также не добавляет director.
3. rejected оставляет один контекст; retry обнуляет сертификат, повтор требует проверки/подтверждения.
4. approved создаёт ровно одну компанию; явное открытие выбирает director-контекст.
5. serviceRole возвращает отдельные назначения multi и null для невыданного ОССиГ первой компании.
6. Открытие АГР от Вектора выбирает employee; попытка team отклоняется.

Прямые отрицательные вызовы проверяют защитные условия, не доказывают существование скрытой кнопки в UI. Сам проверяющий браузерный набор не запускал.

## Пределы результата

Роли, сертификат и реестровые сведения являются fixtures, не результатом реальной интеграции. Формы внутри услуг не реализованы; назначение не доказывает МЧД/право подписи. Условия редактирования юридических полей обозначены как политика UX, не правовой запрет. Поддержка лишь подготавливает обращение. Все данные теряются при прежнем выходе/сбросе/перезагрузке; это не хранение заявок на сервере.

Проверка не доказывает все комбинации произвольной истории, одновременных заявок и производственных прав. Независимый review подготавливает Verification и отдельную приёмку пользователем, не заменяя их.

## Финальная граница организации и сервиса

После последнего уточнения approved-context создаётся с serviceRoles:{}. Независимое исполнение реальных verify → review → submit → approve → open обработчиков подтвердило: организационный kind=director, но serviceRole для АГР/ОССиГ/НСМ равен null, все три карточки показывают отсутствие назначения. Одобрение организации не выдаёт автоматически сервисную роль. В completeConnection UI-теста добавлен соответствующий count=3. Прежние заранее назначенные fixtures остаются самостоятельными демонстрационными исходными данными.

В том же независимом запуске реально отправлено обращение с review-company: scoped notice появился, HTML повторно показывает checkbox без checked. Это подтверждает исправление причины R1, а не только наличие новой строки исходника.
