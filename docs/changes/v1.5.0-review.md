## Замечания первой итерации

R1, P2 — неверная организационно-правовая форма после переключения контекста. organizationDetails() определяет «Индивидуальный предприниматель» по глобальному state.inn, но имя/ИНН организации выводит по выбранному c. После поиска/подключения ИП и возврата к прежнему ООО получается сводка «ООО + исходный ИНН + ИП». Основание: выражение linked&&state.inn?.length===12 в organizationDetails. Необходимо определять форму из выбранного контекста/его ИНН, а не последнего поиска.

Независимо воспроизведено исполнением реальных обработчиков в Node VM: fixture director → вход → personal → поиск 000000000001 → успешное подтверждение → выбрать org → organization. Результат: selected=ООО «Пример», candidateINN=000000000001, в HTML присутствует неверное «Индивидуальный предприниматель». Подменён только DOM, не функции/переходы.

R2, низкая важность — invitationNotice глобален, а люди правильно фильтруются по x.company===state.context.id. После подготовки приглашения в A и перехода в сотрудники B показывается прежняя общая успешная заметка. Это неоднозначная обратная связь, без раскрытия списка чужой организации. Рекомендуется сброс при смене организации или привязка заметки к ID компании.

## Проверенные свойства

- Подтверждённые роли по-прежнему задаются исходными данными стенда, не пользовательским выбором роли. Auth/регистрация не возвращают экран кода или обязательного выбора контекста.
- «Рабочие пространства» — каталог сервисов, не прежний chooser. Кнопки услуг заканчиваются на прежней границе прототипа. Графика SVG синтетическая, реальные пользовательские данные в код не добавлены.
- Сотрудники/финансы включены в меню только director. Render перенаправляет team/finance для неподходящего контекста; sidebar/submit/action повторно ограничивают роли. Ведомственные данные ограничены government, клиентские операции от него отсечены.
- Контакты сохраняются по state.organizationContacts[state.context.id]. Редактируются только phone/email/site, идентификаторы компании и полномочия не меняются. Открытие и submit контактов требуют director, submit дополнительно требует modal=organization.
- Приглашения сохраняются с company=state.context.id, список фильтруется по текущему ID. Требуются фамилия, имя, корректный email аккаунта; отчество необязательно. Новые обязательные телефон/СНИЛС не вводятся только на основании визуального референса.
- Native dialog имеет заголовок, отмену и Escape. go() закрывает состояние modal; смена контекста тоже сбрасывает его. Содержимое приглашений и контактов экранируется. При ошибке используется modal-alert, при сохранении диалог исчезает и виден результат.
- Фильтр каталога/сотрудников скрывает несовпадающие карточки/строки и показывает пустой результат. Это локальная фильтрация данных текущего экрана; серверный поиск не заявляется.
- Профиль и выход остаются в нижней части меню; выход сбрасывает все демо-связи/людей/контакты. Сохранение demoPassword после обычного выхода — прежнее поведение текущего сеанса.

## Перепроверка исправлений

R1 закрыто: организационная форма и должность ИП теперь вычисляются из c.id выбранной записи (org или company-INN), а не из последнего state.inn. Для personal форма не выдумывается и показывается «Не заполнено». R2 закрыто: invitationNotice сохраняет ID компании и отображается только при совпадении с текущим контекстом.

Независимый повтор реальных JS-обработчиков в Node VM passed: директор сохранил контакт и подготовил приглашение A; подключил ИП B; B имеет форму ИП, но не контакт/приглашённого/заметку A; возврат к A показывает ЮЛ и его контакт; personal не может открыть или сохранить contacts. Проверяемые обработчики не подменялись; DOM был заменён, браузерным исполнением это не называется.

Прочитаны актуальные тесты нового каталога/модалок. Добавлены реальные UI-assertions фильтра сервиса/пустой выдачи, создания приглашения, сохранения пользовательского имени при автозаполнении, ошибочного/верного контактного email, Escape, фильтра сотрудников, company-A → ИП-B → company-A и отсутствия переноса контактов/заметки.
