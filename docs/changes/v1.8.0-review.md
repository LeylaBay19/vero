## Проверка требований и guards

- Исправления: исходные значения и предлагаемые company/registration/address/person показаны раздельно. Submit строит новый proposed, не изменяя certificateData. ИНН компании и владельца не представлены редактируемыми полями, в изменяемом списке нет идентификаторов. Пустое предлагаемое значение/отсутствие изменений отклоняются.
- Подтверждение: correction сохраняется по ИНН и сбрасывает connectionReady. Application-submit требует экран review-company, сертификат с текущим ИНН и явный checkbox. correction копируется в снимок заявки, исходные сведения сохраняются отдельно. Принятое предложение применяется к новому контексту только в обработчике approved; на действующей организации автоматическая перезапись не добавлена.
- Необязательная команда: setup-team открывается после подтверждения данных. Добавление/удаление строки привязано к company-INN из connectionReady; send требует тот же объект certificateData. Доступна отправка без сотрудников. До платформенного одобрения нет ни director-context, ни принятого членства сотрудника.
- Очередь: people до одобрения имеют queued, заявка содержит собственный снимок invitees/services. Одобрение меняет queued только для соответствующей компании. Это подготовленное приглашение, не принятый доступ; служебные роли нового директора остаются пустыми. Заявки хранятся по ИНН, повторная отправленная заявка не создаётся заново.
- Отказ/повтор сбрасывает сертификат и connectionReady. Повтор требует новой проверки и подтверждения. Результат платформы по-прежнему применяется только к submitted-заявке из демопанели.
- Постоянные «Приглашения» и «Мои организации» доступны из меню клиента. Решение позже оставляет accepted=false и личный контекст; принятие добавляет только employee с АГК/ОССиГ, без управления командой. В собственную строку таблицы добавлены сервисные назначения отдельно от организационной роли.
- Заявка названа подключением организации, details раскрывает исходные данные, исправления и сотрудников. «Срок проверки уточняется» соответствует сообщённому решению. Вопрос поддержки отделён от формы исправлений, требует текст и сохраняет контекст заявки.
- Общий invite не содержит checkbox выдачи МЧД. Просмотр/черновики не объявляются подписью или юридическим полномочием; отдельные сервисные процессы МЧД пока не реализованы. Во всех услугах сохранена порученная пустая заглушка.

## Независимые выполненные проверки

В Node VM исполнялись реальные обработчики текущего HTML, заменён только DOM. Passed:

1. Отправка вне подтверждённого setup не создаёт заявку.
2. Исправлены все четыре поля: company/registration/address/person; до approval certificateData сохраняет исходные company/address, оба ИНН неизменны.
3. Подтверждение и добавление сотрудника создают queued-строку A, но не организационный контекст.
4. Вторая заявка B с тем же email хранится независимо; одобрение B снимает queued только у B, A остаётся в очереди.
5. Отказ A не добавляет её контекст; retry очищает certificateData и connectionReady.
6. После повторной проверки и approval A в контексте точно применены все четыре предлагаемых значения; исходный сертификат не перезаписан.
7. После одобрения имеются personal + две компании, но не новые employee-memberships; сервисные роли новой компании не выданы.

Прямой отрицательный вызов обработчика проверяет защитное условие, не доказывает наличие скрытой кнопки в UI. Полный browser/layout результат этот запуск не заменяет.
